Key findings

  1. Google Analytics receives the Safe address and the owner address with analytics declined. 118 analytics requests went to Google with consent mode set to denied. 112 of them carry an address: the event parameter ep.safeAddress, the user property up.walletAddress with the connected signer, and the page URL in dl, which holds ?safe=. Declining removes cookies, not the data.
  2. The Safe backend links the IP address to the Safe address continuously while the app is open. On an idle home screen the app sent 17 account-state requests per minute (Safe info, balances, queue, history), about one burst every 15 s. Each carries the Safe address in the URL.
  3. Owner and Safe addresses go to Safe's mainnet RPC during a Sepolia session. 12 requests call the Chainalysis sanctions oracle (isSanctioned) for the Safe and its signers, and 27 requests do ENS reverse lookups, both on rpc.safe.global/1. A custom RPC does not change this path.
  4. Transaction content reaches the backend before the user signs. 12 preview and threat-analysis requests send the full SafeTx (recipient, value, calldata) as typed data, keyed by the Safe address. 2 proposal requests then send the signature. This content has to reach a server to be useful, so only the origin can be hidden.
  5. Opening Swap sends the Safe address to CoW Protocol for 12 chains on two environments. The embedded widget made 172 requests to 9 CoW hosts, including 45 order-history requests and preflights for the Safe address on 12 networks against both api.cow.fi and barn.api.cow.fi. It also looked up the user's IP address and country at api.country.is (2 requests), loaded a Cloudflare Turnstile check, and reported to Sentry (9 of 23 reports carry the Safe address) and LaunchDarkly.
  6. The WalletConnect SDK reports to Reown even when WalletConnect is not used. 19 requests to pulse.walletconnect.org carry a persistent did:key client ID from the first page load.

How we did it

A script played one user through 17 actions on Sepolia: create a 2-of-2 Safe, receive ETH and WETH, send ETH through the multisig flow, swap WETH for COW in the CoW widget, sit idle, and switch to a custom RPC. A second, read-only pass opened a public Safe on mainnet. A recording proxy captured every request, and each request got a privacy tier.…

Chromium (Playwright, fresh profile, QUIC off) ran behind mitmproxy with a trusted CA, so every request from the page, its iframes and its service worker was recorded with headers and bodies. The signer was an injected EIP-1193 provider whose keys and RPC stay outside the browser, so the capture holds only traffic that Safe{Wallet} and its embedded widgets make. A blank-page baseline run identified the browser's own traffic, which is excluded. Identifiers were found by searching URLs, headers and bodies for the Safe address, the owners, the counterparty, safeTxHash, CoW order ids and analytics client IDs. Each request gets the highest tier whose rule it matches, from least to most sensitive:

  1. Address-free. No address or client ID; the receiver still sees the IP address, the time and what was fetched.1,143 requests
  2. Telemetry & fingerprint. A client or device ID that links visits over time, without an address.53 requests
  3. Address-linked read. The Safe address or an owner address, which the receiver links to the IP address.798 requests
  4. Intent before chain. What the user is about to do (recipient, amount, calldata, signature) before it is on chain.62 requests

After a custom Sepolia RPC was set, 34 requests went to the custom node, 11 still went to Safe's RPC (chain status 3, account & contract reads 3, name resolution (ENS) 3), and 73 address-linked reads went to the Safe backend. The setting replaces the chain RPC only.

Recommendations

Recommendations

  1. Stop analytics requests when consent is declined, and drop addresses from events and page URLs in all cases.
    Removes 112 address-linked requests to a third party. No latency cost.
  2. Keep the Safe address out of the URLs the browser fetches.
    97 requests for page code and data carried ?safe= to the web host. Holding the address in client state, or in the URL fragment, keeps it on the device.
  3. Put an Oblivious HTTP relay, run by a separate operator, in front of the Safe backend API.
    The relay sees the IP address and not the request; the backend sees the request and not the IP address. Covers the 444 backend requests, which are the largest share. Adds one relay hop per sequential request, estimated at 120 ms. This answers the concern that anon-RPC alone is partial for a backend-heavy wallet.
  4. Lower the polling rate and make it conditional.
    Poll the Safe info endpoint only, fetch balances and history when its tags change, and back off when the tab is hidden. Fewer samples give an observer fewer IP-to-address links and less timing.
  5. Check sanctions against a local copy of the public list, and resolve names through the user's chosen RPC.
    Removes 12 sanctions requests outright and moves 27 name lookups to the path the user picked. Local checks are faster than a round trip.
  6. Ask the widget to query only the active chain and the production environment, and to geolocate server-side.
    Cuts most of the 45 order-history requests and removes a third party that returns the user's IP address to the page.
  7. Initialize the WalletConnect SDK only when the user picks WalletConnect.
    Removes 19 telemetry requests and a persistent client ID from sessions that use an injected wallet.
  8. For RPC reads that carry an address, add anon-RPC for the origin and PIR for balance, nonce and code.
    106 RPC reads carried an address. Over Tor each sequential read adds about 1.5 s; a PIR balance lookup costs about 1.75 s and 760 KB upload, so PIR fits the few reads the wallet needs on open, not polling.
